xLean App 自动化测试框架

一套「连真机 → 跑 Appium 用例 → 自动出报告 + 趋势」的一键交付框架。测的是 xLean 扫地机器人 App，13 条固定断言用例，零 token，全流程自动跑完、自动生成报告。

12/12 全绿 Appium 3.8 + uiautomator2 零 token · 固定断言 报告 + 趋势自动生成

1项目是什么

这套东西的本质是两条测试线，各有入口和产出：

线测什么成本入口命令产物
Appium 回归 xLean App 的 13 条固定断言用例 零 token run_full_pipeline.py --skip-artemis pipeline_report.html + trend.html
Artemis 探索 手机系统级操作（电量/相机/WiFi） 消耗 token run_full_pipeline.py --skip-appium 同上 + 截图证据

你 99% 的时间只用 Appium 那条线（测 xLean，不花钱）。Artemis 是辅助的 AI 探索，需要额外启动 daemon 且耗 token，日常交付不碰它。

📱
真机测试

Pixel 7 真机 + USB 调试，不依赖模拟器，最接近真实用户场景。

🔁
全自动流水线

跑用例 → 记录历史 → 生成报告 + 趋势，一条命令到底。

📊
专业报告

每条用例含截图证据、耗时、结论；趋势页有稳定率矩阵、失败热点。

🔌
不绑设备

udid: null 自动探测，每个伙伴插自己的手机就能跑。

2三步跑起来

每次跑之前，花 30 秒确认三个前置条件：

1
真机已连

adb devices 能看到一行 57171FDCH009ZC  device（是 device，不是 unauthorized/offline）。空 → 插线 + 手机点「允许 USB 调试」；unauthorized → 点「始终允许」；offline → 拔了重插。

2
Appium Server 已起（端口 4723）

检查：netstat -ano | findstr ":4723" 能看到 LISTENING。没起就开个 PowerShell 窗口跑 .\start_appium.ps1，这个窗口保持开着。

3
（仅 Artemis 需要）daemon 已起

测 xLean 的 Appium 线不需要这个。只有跑 Artemis 探索时才要 uv run artemis ui。

然后，双击 一键测试xLean.bat，或命令行跑：

# 用项目自带 venv 的完整路径，避免 Windows 商店 python 占位符报错
cd C:\Users\xlean\WorkBuddy\2026-09-02-13-57-28\AppAutoTest
& ".\.venv\Scripts\python.exe" run_full_pipeline.py --skip-artemis
跑的时候你会看到：

手机屏幕自己动（反复打开 xLean → 进设置 → 返回 → 进账号页），窗口滚动打印每条用例 PASSED/FAILED。全程 12~20 分钟（每条都要冷启动 App + 建全新会话，这是刻意为之，为了不崩）。

4怎么判断结果

看窗口最后几行 X passed, Y failed：

  • 13 passed, 0 failed → 全绿，健康 ✅
  • 有 failed → 看是几条、哪条，再打开报告看截图定位
判断「是否在跑」的两个可靠信号：

① 手机屏幕自己在动；② 窗口在滚动打印用例名。光看 Appium 刷 GET /status 不算在跑，那只是心跳。

跑的过程中千万别中断！

一点停止/关窗口，Appium 服务就被连带杀掉，又得重新拉起 Appium 重跑，反而更慢。让它自己跑完就行。

7维护更新手册

这是给你（以及后续维护的人）看的——每次 xLean 发版或要改东西时，照着做。

7.1 App 升级了怎么办

1
先跑一轮，看哪些用例 FAIL

双击 一键测试xLean.bat，记下失败的用例名。

2
抓当前页面的真实 UI 结构 
adb shell "uiautomator dump /data/local/tmp/ui.xml"
adb shell "cat /data/local/tmp/ui.xml" | grep -oE 'text="[^"]*"'

这会列出当前屏幕所有文本，看 App 更新后文案/入口变成了什么。

3
对比定位符，更新过时的 text= / content-desc=

去 pages/android_xlean_page.py 改（见 7.3）。

4
优先用「稳定入口」断言

别死磕会变的文案（比如设备名「xLean TR1」），改断「进入设备」这类稳定的入口元素。

实战记录（2026-10-10）：

App 升到 V0.22.6.0 后，首页把「xLean TR1」设备名改成了「进入设备」入口，导致 3 条用例 FAIL。已把断言从 device_name_visible() 改成 home_ready()（判断「进入设备」）。这是典型案例。

7.2 新增 / 改用例

用例文件在 testcases/android/，分两个文件：

  • test_xlean_app.py —— 首页 / 计划 / 探索 / 菜单（6 条）
  • test_xlean_settings_account.py —— 设置页 / 账号页（6 条）

新增一条用例的写法

def test_xxx(home: XLeanHomePage):
    # 1. 用页面对象提供的断言方法
    assert home.is_visible(home._enter_device, timeout=5), "「进入设备」入口缺失"

    # 2. 或用行为级断言（探索页 Compose 无文本时用这个）
    home.goto_explore_tab()
    home.back_to_home()
    assert home.home_ready(), "返回后首页未恢复"
关键：Compose 页面怎么断言

xLean 的探索页是 Compose 渲染，内容区不暴露无障碍文本，所以 text= 断言会失败。遇到这种页面，改用行为级断言（能不能切过去、能不能切回来、首页是否恢复），而不是断具体文案。

7.3 改元素定位

所有元素定位都在页面对象里，别在用例里写死：

文件管什么
pages/android_xlean_page.py首页 / 菜单 / 计划 / 探索的元素定位
pages/android_xlean_settings_page.py设置页 / 账号页的元素定位

定位器用 starts-with(@text, ...) 做前缀匹配，能兼容设备名带后缀（如「xLean TR1 14」）。示例：

# 定位器：兼容「xLean TR1 14」这类带后缀的设备名
_device_name = ("xpath", "//*[starts-with(@text, 'xLean TR1')]")

7.4 改配置

改什么去哪改说明
被测 App 包名 / 启动 Activityconfig/local.yaml个人私有，不入 git
共享配置 / 平台 / 设备config/global.yaml团队共享，入 git
Appium Server 地址config/global.yaml 的 server_url默认 http://127.0.0.1:4723
一个关键配置（别乱改）：

local.yaml 里 unicode_keyboard: false —— 这是实测出来的。xLean 这个 App 在 Appium 自带输入法开启时，UI 树会丢大量元素（「设备设置」「进入设备」全找不到），关掉后 page_source 才正常。中文输入改用 adb shell input text。

7.5 改报告样式 / 趋势页

报告逻辑都在 run_full_pipeline.py：

想改函数
总报告 pipeline_report.htmlwrite_summary()
趋势页 trend.htmlwrite_trend() + _TREND_TPL 模板
历史记录逻辑record_history()

改完后不用重跑测试，直接刷新报告：

& ".\.venv\Scripts\python.exe" run_full_pipeline.py --report-only
改趋势页必看（血泪教训）：

① _TREND_TPL 里 JS 字符串转义引号要写 \\'（四个反斜杠 + 单引号），写 \' 会被 Python 吃掉，导致整个 script 语法错误、页面全空白。② Chart.js 已内嵌进 HTML，别改回 CDN 引用（否则离线/预览加载不到又空白）。③ 改完必须用 scripts/verify_trend.js 真实浏览器渲染验证（0 JS 错误 + 图表实际绘制）再交付，不能只看「文件生成了」。
